# GSD PR Creation Rule

## Purpose

When TASKS.md is updated and **all sub-tasks are completed** (100% completion), automatically
push the feature branch and create a pull request with a well-structured description. This
eliminates the manual step of creating PRs after GSD task execution finishes.

## Trigger Conditions

This rule activates when `.claude/tasks/TASKS.md` is modified. Check for 100% completion by
verifying that:

1. Every sub-task row in the Execution Order table has status `completed`
2. No sub-tasks have status `pending`, `in-progress`, or `blocked`
3. The mermaid dependency graph shows all nodes in the `done` class

## When All Tasks Are Complete

After confirming 100% completion, perform these steps **automatically without asking the user**:

### Step 1: Push the Branch

```bash
git push -u origin <current-branch-name>
```

If the branch is already pushed and up-to-date, skip this step.

### Step 2: Generate PR Description

Build the PR description by reading:

- **TASKS.md** — Extract the phase/sub-task summary table and total counts
- **Git log** — `git log main..HEAD --oneline` to get all commits on the branch
- **REQUIREMENTS doc** — Check `.claude/tasks-archive/` or project root for the original
  `REQUIREMENTS-<branch-name>.md` to pull the high-level summary

### Step 3: Create the PR

Use `gh pr create` with this structure:

```bash
gh pr create --title "<concise title from branch name or requirements>" --body "$(cat <<'EOF'
## Summary

<2-3 sentence description of what this feature branch delivers, derived from the
requirements document or TASKS.md overview>

## Changes

<Bulleted list of phases and what each accomplished, e.g.:>
- **Phase 1**: <summary>
- **Phase 2**: <summary>
- **Phase 3**: <summary>

## Sub-Tasks Completed

| Phase | Task | Description |
|-------|------|-------------|
| 1 | sub-task-1 | <title from sub-task file> |
| ... | ... | ... |

## Commits

<Output of `git log main..HEAD --oneline`, formatted as a list>

## Test Plan

- [ ] Review all changes on the branch
- [ ] Verify documentation accuracy
- [ ] Run full test suite: `npm run verify`
- [ ] Manual smoke test of affected features

---
Generated by GSD task orchestration
EOF
)"
```

### Step 4: Report to User

After PR creation, output the PR URL and a brief summary:

```
PR created: <url>
Branch: <branch-name>
Tasks completed: <N>/<N>
```

## When NOT to Create a PR

- If any sub-tasks are still `pending`, `in-progress`, or `blocked` — do nothing
- If a PR already exists for the current branch — report the existing PR URL instead
- If the user explicitly says not to create a PR — respect that instruction
- If on `main` or `master` branch — never create a PR from the default branch

## Checking for Existing PRs

Before creating a new PR, check if one already exists:

```bash
gh pr list --head <current-branch-name> --state open
```

If a PR exists, update its description instead of creating a duplicate.

## Error Handling

- If `gh` CLI is not authenticated — warn the user and provide `gh auth login` instructions
- If push fails — report the error and suggest manual resolution
- If PR creation fails — report the error with the full `gh` output
